# Phase 10F-2 Direct-Uploadable Fixture Proposal

## 1. Purpose

This proposal defines how a future static physics official-verification fixture pack could become executable. It does not create official PASS evidence by itself.

## 2. Common Fixture Rules

1. Fixtures should be small, bounded, and text-reviewable.
2. Acceptable input forms should match current platform support: small CIF, POSCAR/CONTCAR, or generated pymatgen Structure JSON.
3. Do not add large benchmark files.
4. Do not execute notebooks.
5. Do not execute external scripts or benchmark extraction scripts.
6. Do not call external APIs or require network access.
7. Do not install new dependencies.
8. Expected outputs should be generated once through a reviewed platform flow and checked into a small expected-contract pack only after approval.
9. Official-derived fixtures must retain provenance; internal regression fixtures must not be labeled official.
10. This proposal does not create official PASS evidence until future direct verification executes the approved fixtures through the platform.

## 3. coordination histogram

- tool: `structure.coordination_hist`
- proposed input: one small periodic CIF or POSCAR with stable atom ordering and no disorder.
- expected artifacts:
  - `coordination_hist.json`
  - `coordination_hist_plot.json`
  - `summary.md`
  - `recipe.json`
- expected numeric checks:
  - `structure.site_count`
  - histogram bins by `coordination_number`
  - dominant coordination number and count
  - deterministic `limits` fields
  - no-JS/no-external-URL security flags
- tolerance policy:
  - integer histogram counts exact
  - distances checked only if included and rounded to the adapter precision
- provenance requirement:
  - record whether the input is official-derived, official-like curated, or internal regression.

## 4. XRD

- tool: `structure.xrd`
- proposed input: one small crystalline CIF or POSCAR with full periodic lattice and stable species.
- expected artifacts:
  - `xrd_pattern.json`
  - `xrd_plot.json`
  - `summary.md`
  - `recipe.json`
- expected numeric checks:
  - `schema_version == phase10e4.xrd_pattern.v1`
  - `tool_id == structure.xrd`
  - `radiation == CuKa`
  - peak count within expected cap
  - selected `two_theta_deg` positions within pinned tolerance
  - strongest peak identity and intensity scale
  - no-JS/no-external-URL security flags
- tolerance policy:
  - two-theta tolerance should be pinned before execution, recommended `<= 0.01` degrees for selected peaks unless a future readiness note adjusts it.
  - relative intensity checks should allow documented small floating-point tolerance.
- provenance requirement:
  - record source, transform history, and whether peak expectations were generated by the platform or independently reviewed.

## 5. RDF

- tool: `structure.rdf`
- proposed input: one small periodic crystalline CIF or POSCAR with positive volume and `pbc == [true, true, true]`.
- expected artifacts:
  - `rdf.json`
  - `rdf_plot.json`
  - `summary.md`
  - `recipe.json`
- expected numeric checks:
  - `schema_version == phase10e7.rdf.v1`
  - `tool_id == structure.rdf`
  - `normalization == number_density`
  - r grid and bin count for fixed `r_max_angstrom` and `bin_width_angstrom`
  - selected `g_r` values with documented tolerance
  - normalization metadata including positive volume and number density
  - partial RDF pair ordering when enabled
  - no-JS/no-external-URL security flags
- tolerance policy:
  - bin centers and edges exact after adapter rounding
  - selected `g_r` values checked with fixed numeric tolerance
  - counts exact
- provenance requirement:
  - record input source, lattice/PBC assumptions, and RDF parameter set.

## 6. Approval Gate Before Future Verification

A future Phase 10F-3 or later phase may only create executable evidence after:

- fixture files are approved as bounded and direct-uploadable;
- expected contracts are reviewed for exact/tolerance fields;
- provenance labels are explicit;
- the no-PASS-claim policy is retained until platform execution succeeds;
- no notebook/script/API/network dependency is introduced.
