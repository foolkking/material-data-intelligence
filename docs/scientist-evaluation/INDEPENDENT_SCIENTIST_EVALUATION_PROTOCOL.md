## Frozen candidate

`generated/evaluation_baseline.json` identifies the exact A–I candidate:
canonical HEAD, expected uncommitted H/I fingerprint, schema head, capability
inventory, qualification fingerprints, contracts, prompt versions, provider
configuration and context/repair policy. J preparation files are excluded from
the candidate fingerprint.

Formal answers are in `generated/formal_responses.json`. Every response has a
response hash, evidence-manifest hash and generation metadata. Six provider
attempts failed the bounded validator twice before review and are frozen as
typed “no validated synthesis” responses; they were not replaced by a model,
human or benchmark-specific answer.

## Review sequence

1. Each assigned reviewer completes the four calibration cases.
2. The reviewer completes Pass 1 using only the scientist-facing question,
   response and ordinary source/method/limitation disclosure.
3. An administrator locks Pass 1 and releases the separate Pass 2 file.
4. The reviewer audits evidence, methods, conditions, scope, limitations and
   claim mappings.
5. Completed JSON records are imported with `import-review`. The importer
   checks assignment, baseline, response/evidence hashes, conflict status,
   pass ordering and immutable duplicate protection.
6. Only after the review dataset is complete should `report` calculate
   agreement, material disagreements and maturity gates.

Reviewers are blinded to provider/model, Workstream labels, expected semantics,
validator verdicts, repair history, hidden reasoning and automatic scores.

## Human boundary

The repository must not contain invented reviewer identities, scores,
comments, expertise declarations or validation outcomes. A review is evidence
only after a real independent scientist submits and locks it.
