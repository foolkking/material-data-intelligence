# Adding Scientific Reference Evidence

Use this guide when promoting or revising the scientific qualification of an
existing Capability.

## 1. State the scientific claim

Identify exactly what is being validated:

- a computed value or curve;
- units/conventions;
- an invariant;
- an applicability boundary;
- Artifact serialization;
- ScientificResult projection;
- interpretation or Report behavior.

Do not use “the test passes” as the scientific claim.

## 2. Choose an independent authority

Prefer, in order appropriate to the method:

1. analytical/hand-computable result;
2. genuinely independent implementation;
3. published reference;
4. curated known result with method/version provenance;
5. exact synthetic fixture or physical invariant.

If the platform wraps an upstream library or consumes external-solver output,
use `OFFICIAL_LIBRARY_SEMANTICS` or `EXTERNAL_SOLVER_SEMANTICS` and limit the
claim to the behavior the repository owns. A fixture generated by the same
Adapter is `REGRESSION_ONLY` unless independently checked.

## 3. Record the reference contract

Add a `ScientificEvidenceLink` near the Capability record in
`quality_evidence.py`. Provide:

- stable evidence ID;
- evidence kind;
- test node;
- reference origin, method and version;
- expected scientific semantics;
- units and conventions;
- applicability and limitations;
- explicit tolerance for every numeric assertion.

Do not place large fixture payloads in the manifest. Store them in the existing
family-specific test/evidence location and link the focused test.

## 4. Justify numerical tolerance

Choose absolute, relative or domain bounds from the algorithm and data:

- analytical floating-point accumulation;
- discretization/bin width;
- interpolation or broadening;
- fitting regime;
- stochastic evaluation;
- external-library convention.

Never widen a tolerance merely to obtain a pass. Investigate values outside a
scientifically defensible range.

## 5. Add invariants and negative cases

`DOMAIN_VALIDATED` requires all three:

```text
REFERENCE
INVARIANT
DOMAIN_NEGATIVE
```

Use only scientifically valid invariants: atom/row ordering, periodic
translation, equivalent coordinate representation, paired-row metric
ordering, integral preservation, or deterministic source composition where
appropriate.

Test declared limitations at their boundary. Invalid inputs should resolve to
a typed ineligible/unsupported/failure state before misleading output exists.

## 6. Validate the complete semantic path

Where the Capability produces a ScientificResult, verify:

```text
ScientificObjectVersion
→ Adapter
→ Artifact
→ ScientificResult
```

Check values, units, methods, limitations, Artifact/source refs and exact input
versions. Add interpretation/Report constraints when domain-generic grounding
is insufficient.

## 7. Update the bounded qualification summary

`defaults.py` derives `CapabilityQualification` from the canonical evidence
record. Do not manually duplicate counts or paths in the manifest.

If the scientific contract intentionally changed, update the evidence and then
replace the frozen `qualified_contract_fingerprint` with the newly reviewed
fingerprint. Never update a fingerprint merely to silence
`STALE_QUALIFICATION`.

## 8. Run validation

```powershell
uv run pytest tests/test_scientific_quality_platform.py -q
uv run python scripts/scientific_quality_report.py --check
uv run python scripts/capability_extension_report.py `
  --json-output docs/capabilities/generated/capability_inventory.json `
  --markdown-output docs/capabilities/generated/capability_inventory.md `
  --check
```

Then run the referenced family tests and any relevant service-backed
Artifact/ScientificResult path. Review the generated quality inventory before
claiming a promotion.
